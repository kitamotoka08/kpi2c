# Атрибути:
* User - Користувач:
  *   user_id - унікальний айді користувача (PK, UUID)
  *   username - нікнейм користувача (string)
  *   email - електронна пошта (string)
  *   registered_at - дата реєстрації (date)
* Title - Тайтл (Аніме / Манга):
  *   title_id - унікальний айді тайтла (PK, UUID)
  *   studio_id - (optional, FK, UUID)
  *   name - назва твору (string)
  *   type - тип твору: аніме, манґа, ранобе тощо (string)
  *   episodes_or_chapters - загальна кількість епізодів або розділів (int)
  *   status - статус виходу: триває, завершено, анонсовано (string)
* Genre - Жанр:
  * genre_id - унікальний айді жанру (PK, UUID)
  * genre_name - назва жанру (string)
* UserListEntry - Список користувач:   
  * entry_id - унікальний айді запису (PK, UUID)
  * user_id - посилання на користувача (FK, UUID)
  * title_id - посилання на тайтл (FK, UUID)
  * watch_status - статус: планую, дивлюся, переглянуто, кинуто (string)
  * progress - кількість переглянутих епізодів / прочитаних глав (int)
* Studio - Студія:
  *   studio_id - унікальний айді студії (PK, UUID)
  *   studio_name - назва студії-виробника (string)
  *   country - країна походження (string)
* Review - Відгук:
  *   review_id - унікальний айді відгуку (PK, UUID)
  *   user_id - посилання на користувача, який залишив відгук (FK, UUID)
  *   title_id - посилання на тайтл (FK, UUID)
  *   rating - оцінка від користувача (int)
  *   comment - текст відгуку (string)

# Відносини:
* Studio |o--o{ Title
* Title }|--|{ Genre
* User ||--o{ Review
* Title ||--o{ Review
* User ||--o{ UserListEntry
* Title ||--o{ UserListEntry

# Критерії прийняття
* Нормалізація: Модель відповідає вимогам 3NF
* Ключова узгодженність: Усі PK та FK мають UUID тип даних
* Цілісність данних: Оцінка у відгуках має обмеження 1-5, а для манґи наявність студії необов'язкова.

# Gherkin-сценарії
```
Feature: Керування персональним списком тайтлів

  Scenario: Успішне оновлення прогресу та статусу перегляду
    Given Користувач авторизований у системі
    And Тайтл "Fullmetal Alchemist: Brotherhood" знаходиться у персональному списку користувача зі статусом "Дивлюся" та прогресом 10
    When Користувач змінює прогрес перегляду на 11 та статус на "Дивлюся"
    Then Система зберігає новий прогрес 11 та статус "Дивлюся" у сутності UserListEntry
    And Користувач бачить сповіщення про успішне оновлення

  Scenario: Автоматичне завершення та досягнення максимального епізоду
    Given Користувач авторизований у системі
    And Тайтл має загальну кількість епізодів 64
    When Користувач оновлює прогрес перегляду до 64
    Then Система автоматично змінює статус тайтла на "Переглянуто"
    And Система оновлює прогрес до 64 у базі даних

  Scenario: Помилка при введені невалідного прогресу
    Given Користувач авторизований у системі
    And Тайтл має загальну кількість епізодів 12
    When Користувач намагається встановити прогрес перегляду 15 або від'ємне значення
    Then Система відхиляє запит і не змінює дані в базі
    And Система виводить повідомлення про помилку валідації значення прогресу
```

# EARS-вимоги під ці сценарії
* REQ-01 (Успішне оновлення): WHEN користувач надсилає запит на оновлення прогресу або статусу існуючого запису у списку, SYSTEM SHALL оновити поля progress та watch_status у таблиці UserListEntry та повернути статус успіху.

* REQ-02 (Автозміна статусу): WHILE значення прогресу дорівнює загальній кількості епізодів/глав тайтла, SYSTEM SHALL автоматично встановити watch_status у значення "Переглянуто".

* REQ-03 (Валідація прогресу): WHEN введений progress є меншим за 0 або більшим за максимальну кількість епізодів тайтла, SYSTEM SHALL відхилити транзакцію та видати помилку валідації.

# Нефункціональні вимоги
* NFR-01 (Продуктивність / Час відгуку): Час відповіді сервера на запит оновлення запису у списку не повинен перевищувати 300 мс під час пікового навантаження.
* NFR-02 (Навантаження): Система повинна стабільно обслуговувати до 5000 одночасних активних користувачів, що виконують операції зі списками.
* NFR-03 (Безпека та автентифікація): Усі запити на зміну персональних списків повинні захищатися валідними токенами доступу; прямий доступ без авторизації блокується на рівні шлюзу.
* NFR-04 (Підтримувані пристрої та інтерфейс): Вебдодаток оптимізовано для десктопних і мобільних браузерів з адаптивною версткою під роздільну здатність від 320px до 2560px.
* NFR-05 (Мова та локалізація): Інтерфейс платформи та повідомлення про помилки мають бути українською мовою.
* NFR-06 (Технологічний стек): Бекенд розгортається на базі Node.js із використанням реляційної бази даних PostgreSQL.
